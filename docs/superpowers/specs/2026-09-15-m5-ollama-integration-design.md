# M5 Ollama Compliance Integration Design

## Goal

Integrate the Member 5 compliance-review, Oracle vector-search, and Copilot feature from
`origin/feat/05-member5-updated` into `feat/05-member5-compliance-vector` without replacing the
concrete payment, wallet, KYC, routing, authentication, or messaging implementations already
merged from the other members.

## Scope

The implementation will:

- introduce a focused `com.fluxpay.m5` feature module for the M5 API, application, domain, and
  infrastructure code;
- persist policy documents, chunks, vector-space generations, screening cases, and review-delivery
  state through additive Flyway migrations;
- use Oracle vector search and a concrete Ollama `nomic-embed-text` embedding adapter at runtime;
- expose policy management, compliance assessment, and grounded Copilot endpoints;
- connect payment confirmation and compliance review through an explicit M3-to-M5 bridge that
  delegates to the current concrete payment, KYC, ledger, and transaction boundaries;
- retain deterministic embeddings only in test support, never as a production default.

Out of scope: replacing member-owned payment, wallet, routing, KYC, authentication, Kafka, or
frontend implementations; importing obsolete M5 launchers/security configurations; or changing
existing migration history.

The first delivery does not generate LLM-written answers. A second, follow-on phase will add a
retrieval-augmented generation (RAG) answer generator after this integration is stable. That phase
will retrieve M5 policy chunks, pass only bounded retrieved context to a configured language model,
and require claim-level source citations. It must fall back to the current no-grounded-answer
response whenever retrieval is insufficient or generation cannot be validated.

## Architecture

M5 code is grouped by responsibility below `com.fluxpay.m5`:

- `api`: HTTP controllers and request/response contracts for policy, Copilot, and assessment
  operations.
- `application`: use cases for chunking/indexing policy text, retrieving vector matches, assessing
  payments, and delivering review decisions.
- `domain`: M5 entities, rules, ports, and value objects independent of Spring/JPA transport.
- `infrastructure`: Oracle JDBC/JPA persistence, Ollama HTTP client, Spring configuration, and
  adapters to existing FluxPay services.

The existing `PaymentConfirmationService` remains the payment entry point. Its concrete compliance
port is adapted once to M5, which loads the current payment/KYC data through the established
repositories and returns the M5 review disposition. M5 does not create a second payment workflow,
wallet adapter, or security chain.

## Runtime Configuration

Ollama is the production/default M5 provider:

- endpoint: `http://localhost:11434/api/embed` unless configured otherwise;
- model: `nomic-embed-text`;
- vector dimensions: exactly 768;
- document and query embeddings use the provider's appropriate search prefixes;
- provider failures, malformed payloads, timeouts, and dimension mismatches return typed boundary
  errors and never persist invalid vectors.

The test profile supplies a deterministic embedding implementation. Runtime properties must reject
`mock` as the default/non-test mode and must not silently downgrade to a fake provider.

The initial Copilot response is intentionally extractive: it returns a bounded answer from the
highest-quality retrieved policy material plus citations. This proves that the vector, policy,
authorization, and payment-context integrations work before the later RAG generator introduces a
separate model, prompt, output-validation, and safety surface.

## Persistence and Compatibility

New migrations are additive and use version numbers higher than the current M5 migrations. They
create M5-owned tables/indexes only and preserve all applied member migrations. Oracle vector
queries enforce the configured vector-space identity and dimensions so chunks generated by another
model/configuration are not mixed into a result set.

Existing M5-named legacy source files are either migrated into the focused module or removed only
when no live code references them. Imported source that duplicates merged concrete components is
not retained.

## Error Handling and Security

M5 endpoints reuse the application security context/current-user model. Policy and review actions
apply the same role checks expected by the existing backend. Input limits are validated at the API
boundary. Copilot answers are extractive and cite the matching policy chunks; with no eligible
matches they return a no-grounded-answer response instead of inventing an answer.

The follow-on RAG phase will preserve those citations and must reject generated answers that
reference facts outside the retrieved chunks. It is not a dependency of this integration release.

## Verification

The integration must pass:

- unit tests for chunking, embedding response validation, vector-space compatibility, and Copilot
  grounding;
- repository tests for Oracle SQL/vector query contracts and screening persistence;
- service tests for M3-to-M5 assessment/review delivery and transaction behavior;
- Spring context/controller tests that prove the production wiring selects Ollama and has no M5
  runtime mock bean;
- the existing backend test suite, including unaffected payment, wallet, routing, KYC, and security
  tests.
