FLUXPAY - MEMBER 1 STUDY GUIDE
================================

Purpose
-------
This is a file-by-file guide to the modules you worked on. It explains the
current project code, not an older handoff document. Read it from top to
bottom once, then use the endpoint and viva-question sections before a demo.

Your work is mainly in two tracks:

1. Member 1 identity foundation
   - authentication and JWT
   - user profile
   - user KYC upload and status
   - admin KYC review
   - KYC security gate and wallet provisioning
   - tests and Oracle integration tests

2. Plan 1 support platform
   - support tickets and ticket persistence
   - user and admin ticket APIs
   - provider summary report API
   - user ticket and admin ticket-review frontend

Important current-code note
---------------------------
Older task notes may mention V502, an M1 mock wallet provisioner, or a JSON
KYC metadata endpoint. The current integrated application has evolved:

- Identity/KYC schema is V001__identity_and_kyc.sql.
- Registration uses PersistentWalletProvisioner, which creates real database
  wallet rows for USD, EUR, and INR inside the registration transaction.
- Real KYC submission is multipart/form-data and uploads actual files.
- The old JSON KYC submission mapping still exists only to reject metadata-only
  submissions safely; it is hidden from OpenAPI.

Do not describe the old behavior as the current implementation.

1. BIG PICTURE ARCHITECTURE
====================================================================

Technology
----------
- Backend: Java 17, Spring Boot, Spring MVC, Spring Security, JPA/Hibernate,
  Flyway, Oracle.
- Frontend: Oracle JET, TypeScript, Knockout MVVM, RequireJS.
- Database IDs: Java UUID values are persisted as Oracle RAW(16).
- Authentication: signed HMAC JWT bearer tokens.
- Browser storage: sessionStorage, not a long-lived cookie.

The request path
----------------

  Browser screen / HTML form
          |
          v
  Knockout ViewModel (.ts)
          |
          v
  flux-api.ts request wrapper
          |
          |  Authorization: Bearer <JWT>, when logged in
          |  Idempotency-Key, for protected POST mutations where enabled
          v
  Frontend proxy on :8000
          |
          v
  Spring Security + JwtAuthFilter
          |
          v
  Controller
          |
          v
  Service (business rules, transactions)
          |
          v
  Repository (Spring Data JPA) or JdbcTemplate
          |
          v
  Oracle tables / private document storage
          |
          v
  ApiResponse<T> or ApiError
          |
          v
  flux-api.ts unwraps response.data
          |
          v
  Knockout observables update the HTML view

Standard response shapes
------------------------

Successful API response:

  {
    "correlationId": "...",
    "data": { ... }
  }

Error API response:

  {
    "correlationId": "...",
    "code": "AUTH_REQUIRED",
    "message": "authentication is required",
    "fieldErrors": {},
    "ts": "..."
  }

The correlation ID comes from X-Correlation-ID if the caller supplies it;
otherwise the backend generates one. It is useful when matching a Postman
response to backend logs.

3. DATABASE DESIGN
====================================================================

3.1 Users and authentication
----------------------------

Migration: V001__identity_and_kyc.sql

Table: users
  id             RAW(16) primary key
  email          VARCHAR2(255), not null
  password_hash  VARCHAR2(255), not null
  role           VARCHAR2(50), default USER
  full_name      VARCHAR2(255), not null
  created_at     timestamp
  updated_at     timestamp

Rules:
- The normal unique email constraint prevents exact duplicates.
- uq_users_email_canonical is a function-based unique index on
  LOWER(TRIM(email)). It prevents duplicates such as:
    Alice@Example.com
    alice@example.com
    " alice@example.com "
- password_hash stores the BCrypt hash, never the plaintext password.
- trg_users_updated_at is an Oracle trigger that refreshes updated_at on a
  user update.
- user_roles and refresh_tokens are present in the baseline schema. The
  current login flow uses the users.role string and short-lived JWT, not a
  refresh-token endpoint.

Why RAW(16)?
----------------
Oracle has no native UUID column type. A UUID is 16 bytes, so the entity uses:

  @JdbcTypeCode(Types.BINARY)
  @Column(columnDefinition = "RAW(16)")

Hibernate converts Java UUID <-> Oracle RAW(16). This uses less space and is
more structured than putting UUID text in VARCHAR2(36).

3.2 KYC tables
--------------

Table: kyc_cases
  id               RAW(16) primary key
  user_id          RAW(16) FK users(id), unique
  status           PENDING | VERIFIED | REJECTED
  doc_type         PASSPORT | AADHAAR | PAN | DRIVING_LICENSE
  doc_number       VARCHAR2(64)
  created_at
  submitted_at
  decided_by       RAW(16) FK users(id), nullable while pending
  decided_at       nullable while pending
  reject_reason    nullable except rejected cases
  version          NUMBER, optimistic version counter

Important constraints:
- One KYC case per user: uq_kyc_cases_user.
- A PENDING case has no reviewer/time/reason.
- A VERIFIED case has reviewer and time, no reject reason.
- A REJECTED case has reviewer, time, and a reject reason.
- idx_kyc_cases_queue(status, submitted_at, id) supports the admin queue.

Table: kyc_documents
  id               RAW(16) primary key
  case_id          RAW(16) FK kyc_cases(id), cascade delete
  file_name        safe client filename
  file_type        application/pdf | image/jpeg | image/png
  file_size        > 0 and <= 5 MiB
  storage_url      private storage key, normally local:<uuid>
  uploaded_at

The database stores document metadata and a storage key. Binary document bytes
are stored privately on disk in the configured KYC storage directory, not in a
public static directory and not exposed by a URL.

3.3 Support-ticket tables
-------------------------

Migration: V006__support_tickets.sql

Table: support_tickets
  id                 RAW(16) primary key
  user_id            RAW(16) FK users(id)
  payment_id         RAW(16) FK payments(id), optional
  subject            VARCHAR2(120)

4. SECURITY - WHAT PROTECTS THE SYSTEM
====================================================================

4.1 Password protection
-----------------------

Location: AuthService.java and SecurityConfig.java

- SecurityConfig creates BCryptPasswordEncoder.
- AuthService.register calls passwordEncoder.encode(request.password()).
- The hash is saved in users.password_hash.
- AuthService.login calls passwordEncoder.matches(enteredPassword, hash).
- BCrypt is salted, so two equal passwords normally produce different hashes.
- BCrypt only safely accepts up to 72 UTF-8 bytes. The service checks this
  explicitly before hashing and before matching.
- The plaintext password is never returned by API responses.
- On the frontend the password is only held in the active Knockout input
  observable. AuthPage clears it when the auth screen disconnects.

4.2 JWT lifecycle
-----------------

JWT creation: common/security/JwtUtil.java

Claims in the signed token:
  sub   = user UUID
  email = canonical user email
  role  = USER or ADMIN
  iat   = issued time
  exp   = issued time + 3600 seconds

The signing key comes from fluxpay.jwt-secret, whose environment input is
JWT_SECRET. The secret must be at least 32 bytes for an HMAC key.

JWT request flow:

1. Login/register succeeds.
2. AuthResponse contains token, tokenType "Bearer", expiresIn 3600, and user.
3. Frontend session.set stores token under sessionStorage['fluxpay.token'].
4. flux-api.ts adds Authorization: Bearer <token> to authenticated requests.
5. JwtAuthFilter validates signature and expiry.
6. It builds CurrentUser(userId, email, role).
7. It puts ROLE_USER or ROLE_ADMIN in Spring Security's SecurityContext.
8. Controllers receive CurrentUser through @AuthenticationPrincipal.

JWT failure behavior:
- Missing token on a protected endpoint -> 401 AUTH_REQUIRED.
- Invalid signature or malformed token -> filter clears security context,
  SecurityConfig returns 401 AUTH_REQUIRED.
- Expired token -> same 401 response.
- The response intentionally does not expose parser internals or token details.
- A role in a JWT is a signed claim. Current code does not re-check the user
  role in the database for every request and has no refresh/logout revocation
  endpoint. A changed role takes effect after a new login/token or expiry.

4.3 HTTP and method security
----------------------------

SecurityConfig.java:
- CSRF disabled because this is a stateless bearer-token API.
- Session creation policy is STATELESS.
- Public paths:
    /api/auth/**
    /swagger-ui.html
    /swagger-ui/**
    /v3/api-docs/**
- All other endpoints require authentication.
- JSON error handlers return:
    401 AUTH_REQUIRED
    403 FORBIDDEN

MethodSecurityConfig.java enables @PreAuthorize.

Examples:
- AdminKycController has @PreAuthorize("hasRole('ADMIN')").
- AdminTicketController has @PreAuthorize("hasRole('ADMIN')").
- AdminReportController has @PreAuthorize("hasRole('ADMIN')").

Frontend role checks are only for user experience. They do not secure data.
The backend is the final authority.

4.4 Ownership protection
------------------------

Examples:
- User profile endpoints do not accept a user ID. They use CurrentUser.userId.
- Ticket GET uses findByIdAndUserId(ticketId, currentUserId). A different user
  gets 404 TICKET_NOT_FOUND, not 403. This avoids revealing that a ticket
  exists.
- A related ticket payment must pass findByIdAndSenderId(paymentId, userId).
- KYC document content can be read only by its owner or a literal ADMIN role.
  A different normal user gets a deliberate 404.

4.5 File upload security
------------------------

KycDocumentStorage.java protects uploads by validating:
- exactly one to four files per submission;
- nonempty file and maximum 5 MiB each;
- MIME type PDF/JPEG/PNG;
- valid safe filename: no path slash, backslash, control character, or blank;
- PDF header (%PDF-) and EOF marker;
- actual JPEG/PNG decode through ImageIO, not only the claimed MIME type;
- image maximum 25 megapixels;
- UUID-based filename in private storage;
- no symbolic storage directory/file traversal;
- Cache-Control: no-store, X-Content-Type-Options: nosniff and sandbox CSP
  on document downloads.

4.6 Correlation IDs
-------------------

CorrelationIdFilter.java:
- Reads X-Correlation-ID if supplied.
- Generates a UUID if omitted.
- Places it in logging MDC and response header.
- ApiResponse and ApiError expose the same ID.

Use this during debugging: copy the correlation ID from Postman and search the
backend terminal logs.

5.1 Registration
----------------

Frontend route and files
  URL:          http://localhost:8000/?ojr=register
  ViewModel:    frontend/fluxpay-ui/src/ts/viewModels/register.ts
  View:         frontend/fluxpay-ui/src/ts/views/register.html
  Shared logic: frontend/fluxpay-ui/src/ts/services/page.ts, signUp()
  API facade:   frontend/fluxpay-ui/src/ts/services/flux-api.ts, register()

Backend files
  Controller:   backend/.../controller/AuthController.java
  Service:      backend/.../service/AuthService.java
  DTO:          backend/.../dto/RegisterRequest.java
  Repositories: UserRepository, KycCaseRepository, WalletRepository

Browser-to-database sequence
----------------------------

1. The register.html form binds name/email/password to Knockout observables.
2. register.ts extends AuthPage, which extends Page. Page.signUp() runs.
3. Page.signUp validates that all three fields have values.
4. fluxApi.register sends:

     POST /api/auth/register
     Content-Type: application/json

     {
       "fullName": "Alice Example",
       "email": "Alice@Example.com",
       "password": "a-password-at-least-8-chars"
     }

5. AuthController uses @Valid and passes RegisterRequest to AuthService.
6. AuthService canonicalizes email with trim().toLowerCase(Locale.ROOT).
7. UserRepository.existsByCanonicalEmail uses lower(trim(email)) to check both
   existing legacy rows and new canonical values.
8. If duplicate, AuthException EMAIL_EXISTS is mapped to HTTP 409.
9. AuthService checks password byte length <= 72 UTF-8 bytes.
10. It creates User with:
      - random UUID
      - canonical email
      - BCrypt password hash
      - role hardcoded to USER
      - trimmed full name
      - created/updated timestamps
11. users.saveAndFlush writes the user.
12. walletProvisioner.provision(userId) creates/finds USD, EUR, INR CUSTOMER
    wallets through PersistentWalletProvisioner.
13. The transaction commits only if both user and wallet provisioning succeed.
    If provisioning throws an exception, registration rolls back.
14. AuthService creates a one-hour JWT and UserResponse with KYC status NONE.
15. AuthController returns HTTP 201 ApiResponse<AuthResponse>.
16. Page.signUp calls session.set(response): token goes to sessionStorage and
    user data goes to the Knockout session observable.
17. Frontend navigates to ?ojr=kyc.

What an interviewer may ask
---------------------------

Q: Can somebody make themselves ADMIN by sending role=ADMIN during signup?
A: No. RegisterRequest has no role property and AuthService always uses the
   constant USER_ROLE = "USER". The server owns role assignment.

Q: Why canonicalize email in both code and database?
A: Code gives friendly, consistent behavior. The Oracle function-based unique
   index protects against race conditions and legacy/non-canonical rows.

Q: Why saveAndFlush before wallet provisioning?
A: It makes database issues surface before subsequent provisioning work. The
   entire method remains one transaction, so a provisioning failure rolls it
   back.

5.2 Login
-----------

Frontend route/files
  URL:          ?ojr=login
  ViewModel:    viewModels/login.ts
  View:         views/login.html
  Logic:        Page.signIn()

Request:

  POST /api/auth/login
  {
    "email": " Alice@Example.com ",
    "password": "..."
  }

Backend flow
------------

1. AuthService canonicalizes email with trim + lowercase.
2. UserRepository.findByCanonicalEmail finds lower(trim(email)).
3. BCryptPasswordEncoder.matches checks password against password_hash.
4. A nonexisting email and a wrong password both return the same error:

     HTTP 401
     code: INVALID_CREDENTIALS
     message: invalid email or password

   This prevents account-existence disclosure.
5. KycCaseRepository finds the user's current KYC case. If absent, KYC status
   is NONE.
6. AuthService returns a fresh one-hour JWT and current UserResponse.
7. session.set saves token/user. RootViewModel later redirects an admin who
   reaches dashboard to the Administration route.

Legacy email answer
-------------------

Login supports padded/mixed-case values because AuthService canonicalizes the
input and the repository query uses LOWER(TRIM(email)). The @Email annotation is
on RegisterRequest, not LoginRequest, so a valid legacy stored address can be
normalized at login rather than rejected prematurely by email validation.

7. KYC USER MODULE - COMPLETE WORKFLOW

7.1 State model
---------------

No KYC case              -> response status NONE
First valid upload       -> PENDING
PENDING or VERIFIED      -> documents are read-only; new upload rejected
Admin rejection          -> REJECTED
Valid resubmit from REJECTED -> PENDING and decision fields reset
Admin approval           -> VERIFIED

The current real upload service reports a conflict if a PENDING/VERIFIED case
is overwritten. This is the correct current behavior for file-backed KYC.

7.4 Real KYC submission - multipart upload
-------------------------------------------

Correct current request:

  POST /api/kyc/applications
  Content-Type: multipart/form-data
  Authorization: Bearer <JWT>

  form-data fields:
    docType     PAN | AADHAAR | PASSPORT | DRIVING_LICENSE
    docNumber   text up to 64 characters
    files       one to four actual file parts

Controller: KycDocumentController.submit()
Service:    KycUploadService.submit()

Step-by-step:
1. kyc.html accepts only PDF/JPG/PNG and allows multiple files.
2. kyc.ts checks client-side: one to four, correct MIME type, nonzero, <=5 MiB.
3. fluxApi.uploadKyc creates FormData with docType, docNumber, and repeated
   files parts. It does not set JSON Content-Type for FormData.
4. KycDocumentController gets @RequestParam docType/docNumber and
   @RequestPart("files") List<MultipartFile>.
5. KycUploadService validates details and locks the user row first. Locking the
   user matters because a first KYC submission does not yet have a KYC case row
   to lock.
6. It locks the existing KYC case if it exists.
7. If case is absent, it creates a new PENDING KycCase.
8. If case is REJECTED, KycCase.resubmit changes it to PENDING, refreshes
   document type/number/submitted time, and clears reviewer/time/reject reason.
9. If case is PENDING or VERIFIED, it returns KYC_CONFLICT. The user must wait
   or be rejected before replacing actual documents.
10. KycDocumentStorage.validate validates file name, bytes, real format, and
    file size.
11. Each byte array is stored under a generated UUID .bin file in private
    storage; kyc_documents records local:<uuid>, name, type, size, timestamp.
12. Old document database rows are replaced. Old physical files are removed
    only after a successful commit. New physical files are removed on rollback.
13. Service returns KycStatusResponse (HTTP 201 through the controller).
14. kyc.ts clears selected files/number, updates its KYC observable, then calls
    session.restore() so the header/profile's kycStatus is refreshed.

Why two /api/kyc/applications controller mappings exist
--------------------------------------------------------

- KycDocumentController handles consumes=multipart/form-data and is the real
  endpoint.
- KycController has consumes=application/json but is @Hidden in OpenAPI and
  deliberately throws VALIDATION with a message that actual files are required.

This prevents an old client from pretending that metadata-only KYC documents
were uploaded. In a demo or viva, always use multipart/form-data.

7.5 Secure document content endpoint
-------------------------------------

  GET /api/kyc/documents/{documentId}/content
  Authorization: Bearer <JWT>

Flow:
1. KycUploadService.read finds document metadata by id.
2. If caller is not ADMIN and does not own document.kycCase.userId, it throws
   KYC_NOT_FOUND. A normal user cannot discover another user's document.
3. Storage reads the UUID-based private file.
4. Controller returns attachment bytes with no-store, nosniff and sandbox CSP.
5. frontend fluxApi.kycDocument fetches Blob bytes.
6. Page.openDocument creates a temporary Blob URL for preview.
7. Page.closeDocument revokes the Blob URL; session changes also close it.

7.6 DatabaseKycGate integration
--------------------------------

File: backend/src/main/java/com/fluxpay/service/DatabaseKycGate.java

  boolean isVerified(UUID userId)

returns true only when a kyc_cases record exists and status == VERIFIED.

It is consumed by PaymentService, PaymentConfirmationService, and
BankAccountPostingService. This means KYC does more than update a profile badge:
later money operations can deny nonverified users with KYC-required errors.

8. ADMIN KYC REVIEW MODULE - COMPLETE WORKFLOW
====================================================================

Admin API endpoints
-------------------

  GET /api/admin/kyc/applications?status=PENDING&page=0&size=50
  PUT /api/admin/kyc/applications/{id}/approve
  PUT /api/admin/kyc/applications/{id}/reject

All require a JWT with role ADMIN.

List endpoint
-------------

Controller: AdminKycController.listApplications()
Service:    KycService.listForAdmin()

- Filter is case-insensitive.
- ALL is accepted to list all statuses.
- page must be >= 0.
- size must be 1 to 100.
- Queue ordering is submittedAt ascending, then id ascending, so oldest pending
  cases come first.
- Each KycAdminRow has applicant email/name, document metadata, state, dates,
  reason and optimistic version.

Frontend integration
--------------------

  URL:       ?ojr=admin
  ViewModel: frontend/fluxpay-ui/src/ts/viewModels/admin.ts
  View:      frontend/fluxpay-ui/src/ts/views/admin.html
  Shared KYC review actions: frontend/.../services/page.ts

Page.load() restores the session, checks session.isAdmin for the UI, calls
fluxApi.adminKyc, and displays the queue. The backend still enforces the role
even if someone manually enters the route URL.

Approve endpoint
----------------

  PUT /api/admin/kyc/applications/{id}/approve
  {
    "expectedVersion": 0,
    "reason": null
  }

Flow:
1. @PreAuthorize verifies ADMIN.
2. CurrentUser supplies reviewer ID.
3. KycService.reviewableCase uses findByIdForUpdate to lock the row.
4. It requires expectedVersion equal to KycCase.version.
5. It requires current status PENDING.
6. It loads submitted documents, requires real local storage keys, and reads
   every stored file. Approval cannot pretend unavailable originals exist.
7. KycCase.approve sets VERIFIED, reviewer, decision time, and clears reason.
8. JPA @Version increments when persisted.

Reject endpoint
---------------

  PUT /api/admin/kyc/applications/{id}/reject
  {
    "expectedVersion": 0,
    "reason": "Please upload a clearer PAN image."
  }

Rules:
- expectedVersion is mandatory and >= 0.
- reason must be nonblank and max 500 characters.
- Reject writes REJECTED, reviewer, decision time, reason, and increments
  version.
- The user may then upload corrected documents. resubmit clears all prior
  decision fields and returns the case to PENDING.

Why expectedVersion is needed
-----------------------------

Suppose two admins load version 0. Admin A approves first; the entity becomes
version 1. Admin B sends a decision using expectedVersion 0. The service sees a
stale version and returns HTTP 409 KYC_CONFLICT instead of overwriting A's
decision. Pessimistic row locks plus optimistic version comparison provide safe
review behavior.

9. PLAN 1 SUPPORT TICKETS - COMPLETE WORKFLOW
====================================================================

9.1 User ticket API
-------------------

  POST /api/tickets
  GET  /api/tickets?page=0&size=20
  GET  /api/tickets/{id}

All require an authenticated user. Successful output is wrapped in ApiResponse.

Create request:

  POST /api/tickets
  Authorization: Bearer <user JWT>
  Idempotency-Key: a-client-generated-unique-key
  Content-Type: application/json

  {
    "paymentId": "optional-UUID-of-user-owned-payment",
    "subject": "Payout status request",
    "body": "Please review my payout processing status."
  }

Create flow
-----------

1. TicketController.create obtains CurrentUser and Idempotency-Key.
2. PaymentOperationService.requireKey requires 1 to 255 nonblank characters.
3. @Valid checks DTO shape; TicketService additionally trims and validates:
      subject: 1 to 120 characters
      body:    1 to 4000 characters
4. If paymentId is included, TicketService calls
   PaymentRepository.findByIdAndSenderId(paymentId, currentUserId).
5. If user does not own that payment, it returns 404 PAYMENT_NOT_FOUND.
6. TicketService sends the work through PaymentOperationService.execute:
      action = CREATE_TICKET
7. The durable operation record is keyed by (user_id, client_key).
8. The supplier creates SupportTicket with default status OPEN and timestamps.
9. Ticket and saved API response commit transactionally.
10. Controller returns HTTP 201 plus TicketResponse.

Idempotency behavior
--------------------

Same user + same key + same normalized request:
  returns the saved original TicketResponse instead of creating a duplicate.

Same user + same key + different request:
  HTTP 409 IDEMPOTENCY_CONFLICT.

Same key while original request is incomplete:
  HTTP 409 OPERATION_IN_PROGRESS.

This is important because browser retries or user double-clicks should not create
two identical tickets.

Owner-only reads
----------------

TicketService.getOwned uses SupportTicketRepository.findByIdAndUserId.

  GET /api/tickets/{id}

works only for the owner. A ticket belonging to a different user returns:

  HTTP 404
  code: TICKET_NOT_FOUND

It deliberately does not return 403, because 403 would reveal that the guessed
ticket exists.

9.2 User ticket frontend
------------------------

Routes and files
  URL:       ?ojr=tickets
  ViewModel: frontend/fluxpay-ui/src/ts/viewModels/tickets.ts
  View:      frontend/fluxpay-ui/src/ts/views/tickets.html
  API:       ticketApi at end of services/flux-api.ts

How a user reaches it
---------------------
- Account page: "Support tickets" link.
- Profile dropdown: "Help & support" for a normal user.
- Direct route: ?ojr=tickets.

TicketsViewModel behavior
-------------------------

On load it:
1. GETs /api/tickets?page=0&size=20.
2. Fetches all paged own payments using /api/payments?page=N&size=100.
3. Fetches own recipients using /api/recipients.
4. Filters out DRAFT and QUOTED payments.
5. Builds optional payment labels in this exact visual format:

     [date - recipient name - amount]

   Example:

     [9/21/2026 - Riya Patel - $125.00]

The related payment is a select/dropdown, not a free-text input. The client only
shows the signed-in user's submitted transactions. The server repeats the owner
check so client filtering cannot be bypassed.

On submit it trims/validates subject/body, omits paymentId when blank, calls
ticketApi.create(), clears the form, and refreshes the ticket list.

The current user ticket view displays the first 20 ticket records and their
total count. It does not currently provide user-side pagination controls.

9.3 Administrator ticket API
----------------------------

  GET /api/admin/tickets?status=ALL&page=0&size=20
  PUT /api/admin/tickets/{id}

Class: AdminTicketController.java
Class-level security: @PreAuthorize("hasRole('ADMIN')")

Update request:

  {
    "status": "IN_PROGRESS",
    "assigneeAdminId": "optional-admin-uuid"
  }

Rules enforced by TicketService
-------------------------------
- status must be OPEN, IN_PROGRESS, RESOLVED, or CLOSED.
- Optional assigneeAdminId must identify an existing user whose role is ADMIN.
- If assigneeAdminId is omitted, status changes but existing assignment stays.
- This API currently has no explicit way to clear an existing assignment.
- Any valid status can generally be set, except CLOSED tickets must first move
  to OPEN before any other status. A CLOSED -> OPEN reopen is allowed.
- There is no ticket expectedVersion field; ticket state safety is different
  from KYC review's optimistic-version flow.

9.4 Admin ticket frontend
-------------------------

  URL:       ?ojr=admin-tickets
  ViewModel: frontend/fluxpay-ui/src/ts/viewModels/admin-tickets.ts
  View:      frontend/fluxpay-ui/src/ts/views/admin-tickets.html

The profile menu exposes "Support review" to ADMIN users.

AdminTicketsViewModel:
- restores session if needed;
- does not call admin APIs if session.isAdmin is false;
- lists/filter/pages ticket queue in groups of 20;
- uses current admin's own ID for "Assign to me";
- sends PUT updates for user-interface lifecycle buttons:

    OPEN        -> IN_PROGRESS  (Start)
    IN_PROGRESS -> RESOLVED     (Resolve)
    RESOLVED    -> CLOSED       (Close)
    CLOSED      -> OPEN         (Reopen)

9.5 Admin report API
--------------------

  GET /api/admin/reports/provider-summary?from=<ISO-8601>&to=<ISO-8601>

Example:

  /api/admin/reports/provider-summary?from=2026-09-01T00:00:00Z&to=2026-10-01T00:00:00Z

Controller: AdminReportController.java
Service:    ReportQueryService.java

It is ADMIN-only and read-only. JdbcTemplate executes a grouped query over

There is no current dedicated report frontend screen. This capability is API
and backend-test ready; it can be exercised from Swagger/Postman.

10.3 Frontend session flow
--------------------------

File: frontend/fluxpay-ui/src/ts/services/session.ts

session.set(authResult):
  sessionStorage['fluxpay.token'] = authResult.token
  session.user(authResult.user)
  dispatches fluxpay:session

session.restore():
  if a token exists, calls GET /api/users/me
  fills session.user from the safe server response

session.clear():
  removes the token
  clears the observable user
  dispatches fluxpay:session

On any non-auth HTTP 401, flux-api.ts removes the token and emits
fluxpay:expired. session.ts handles that by clearing session and navigating
home. Thus an expired JWT cannot keep the UI looking logged in.

10.4 flux-api.ts request wrapper
--------------------------------

File: frontend/fluxpay-ui/src/ts/services/flux-api.ts

The request<T>() helper:
- uses a relative API path so development proxy can forward it;
- adds Accept: application/json;
- adds Content-Type: application/json for JSON bodies;
- skips JSON content type for FormData uploads;
- adds Authorization bearer header when a token exists;
- unwraps ApiResponse by returning json.data;
- combines API message and fieldErrors for frontend error display;
- clears session after a protected 401;
- adds an Idempotency-Key for calls using idem=true.

The in-memory pending map chooses crypto.randomUUID keyed by method + path +
body. A retry of the same in-flight equivalent call gets the same key. The
backend remains authoritative because it stores completed operation snapshots.

13. VIVA / INTERVIEW ANSWERS
====================================================================

Q: Explain registration from UI to database.
A: The register view binds inputs to a Knockout ViewModel. Page.signUp calls
   fluxApi.register, which sends POST /api/auth/register. AuthController
   validates the DTO and calls AuthService. AuthService canonicalizes email,
   checks duplicate email using lower(trim(email)), BCrypt-hashes the password,
   creates only a USER, saves it, provisions USD/EUR/INR wallets in the same
   transaction, and returns a one-hour JWT. The frontend stores the JWT only in
   sessionStorage and navigates to KYC.

Q: How is the password saved?
A: AuthService uses BCryptPasswordEncoder.encode. Only the BCrypt hash goes
   into users.password_hash. Login uses BCrypt matches; plaintext is never
   stored or returned.

Q: Why is email canonicalization important?
A: It makes " Alice@Example.com " and "alice@example.com" the same identity.
   Both Java repository queries and Oracle's function-based unique index use
   lower(trim(email)), which prevents case/space duplicate accounts.

Q: How does backend know who made a request?
A: JwtAuthFilter validates the bearer token, creates CurrentUser from signed
   claims, and puts it in Spring Security context. Controllers inject it using
   @AuthenticationPrincipal rather than trusting a client-supplied user ID.

Q: What happens if JWT is invalid or expired?
A: The filter clears the security context; protected endpoints return JSON 401
   AUTH_REQUIRED. The frontend removes the token, clears the session, and
   navigates home.

Q: How do you stop normal users reaching admin endpoints?
A: SecurityConfig requires authentication for all protected APIs and
   MethodSecurityConfig enables @PreAuthorize. Admin controllers use
   hasRole('ADMIN'), based on ROLE_ADMIN placed by JwtAuthFilter. A USER gets
   JSON 403 FORBIDDEN.

Q: Explain the KYC upload security.
A: It is multipart file upload, not client-provided metadata only. The backend
   limits file count/size/types, checks actual PDF/image bytes, validates file
   names, stores bytes in private UUID-named files, saves only metadata/storage
   key in Oracle, prevents path traversal/symlinks, and lets only owner/admin
   fetch a document with no-store/nosniff/sandbox headers.

Q: How do you prevent two admins making conflicting KYC decisions?
A: The case is loaded with a pessimistic lock and request carries expectedVersion.
   The service compares version/status before decision. A stale request returns
   409 KYC_CONFLICT. KycCase also has JPA @Version.

Q: Why does cross-user ticket access return 404, not 403?
A: A 403 reveals that a guessed ticket ID exists. Repository query includes both
   id and owner ID, so a nonowner gets the same not-found response as an absent
   ticket.

Q: How does ticket idempotency work?
A: POST requires Idempotency-Key. PaymentOperationService stores a normalized
   request and final response in payment_operations. Same key/same request
   replays saved result; same key/different request gives 409 conflict. This
   prevents duplicate tickets from retries or double clicks.

Q: How does the payment dropdown avoid wrong payment IDs?
A: TicketsViewModel fetches only the signed-in user's payments and recipients,
   filters non-submitted DRAFT/QUOTED items, and displays a date-recipient-amount
   label. TicketService independently checks payment ownership by sender ID,
   so changing browser data cannot attach another user's payment.

Q: Is automatic ticket creation for a failed payment implemented?
A: No. Current scope is manual user ticket creation. It was intentionally not
   added to payment failure flow.

Q: Is ticket reply/chat implemented?
A: No. support_ticket_messages entity/repository/schema exist, but no endpoint
   or frontend conversation UI currently uses them.

Q: Does Plan 1 have a report UI?
A: It has an ADMIN-only provider-summary backend endpoint and tests. There is
   not yet a dedicated frontend report page.
